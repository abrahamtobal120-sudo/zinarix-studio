# Zinarix Studio — Plan de 20 fases

**Fecha:** 2026-11-15 · **Versión base:** 0.6.1

> Fases 1–15: funciones (agente, editor, IA, video, 3D, lanzamiento).
> Fases 16–20 (agregadas después): **interfaz**. Ver Parte 5 (qué es código abierto), Parte 6 (cómo está la interfaz hoy) y Parte 7 (las 5 fases nuevas).

Este plan sale de estudiar ocho productos y compararlos con lo que Zinarix Studio ya tiene. Lo que se toma de cada uno son **ideas de función y de flujo de trabajo**, no su marca, su código ni su diseño visual.

Cómo interpreté los nombres de la solicitud:

| Escrito | Producto | Área |
|---|---|---|
| imovi | Apple iMovie | Edición de video sencilla |
| vlender | Blender | 3D, animación y render |
| avinchi | DaVinci Resolve | Edición y color profesional |
| cursor | Cursor | Editor con IA |
| vstudio | Visual Studio Code | Editor base |
| aogle ai studio | Google AI Studio | Pruebas de modelos y generación |
| gpt codex | OpenAI Codex | Agente de código (CLI, nube, IDE) |
| calude codex | Claude Code | Agente de código (CLI, IDE, SDK) |

## Parte 1 — Estudio de funciones

### 1.1 Cursor
- **Tab / next edit:** predice la siguiente edición (varias líneas a la vez), salta al siguiente punto que hay que cambiar e importa símbolos solo.
- **Agente:** edita varios archivos, ejecuta en la terminal, guarda *checkpoints* para volver atrás, tiene modo plan y lista de tareas.
- **Reglas:** `.cursor/rules/*.mdc`, que se aplican siempre, por patrón glob o cuando el agente las pide; también lee `AGENTS.md`.
- **Contexto con @:** archivos, carpetas, documentación indexada, web, git, terminal y Problemas.
- **Índice semántico del código** con embeddings, que se actualiza poco a poco.
- **Background agents:** agentes que corren en una VM remota sobre una rama propia y terminan abriendo un PR.
- **Bugbot:** revisión automática de PRs en GitHub.
- MCP, memorias e integraciones con Slack y Linear.

### 1.2 Visual Studio Code
- Editor (multicursor, minimapa, *sticky scroll*), LSP, **DAP** (depurador), **Tasks** (`tasks.json`), **Test Explorer**, **notebooks** de Jupyter.
- Extensiones (Marketplace / Open VSX), perfiles, sincronización de ajustes, Remote (SSH, Dev Containers, WSL) y Live Share.
- Copilot integrado: chat, agent mode, edits, MCP, `copilot-instructions.md` y *prompt files*.

### 1.3 Google AI Studio
- **Playground:** system instructions, temperatura, top-p, salida estructurada con JSON Schema, *function calling*, *grounding* con búsqueda, ejecución de código y contexto largo (video, audio y PDF dentro del prompt).
- **Comparar** dos modelos lado a lado.
- **Stream / Live:** conversación por voz y cámara en tiempo real, o compartiendo la pantalla.
- **Generación de medios:** imagen (Imagen / Gemini Image), video (Veo), voz (TTS con varios hablantes) y música.
- **Build:** crea una app web desde un prompt, con vista previa en vivo y opción de publicarla.
- "Get code": convierte el prompt actual en código del SDK. También guarda historial y prompts compartibles.

### 1.4 OpenAI Codex
- **CLI** con niveles de aprobación (solo lectura / auto / acceso total) y **sandbox** del sistema operativo (Seatbelt, Landlock).
- **Codex Cloud:** tareas en paralelo dentro de contenedores aislados; cada una entrega un diff o un PR.
- **Code review** de PRs y `codex exec` para usarlo sin interfaz en CI.
- `AGENTS.md` jerárquico (raíz → subcarpetas), MCP, reanudar sesiones y adjuntar imágenes al prompt.

### 1.5 Claude Code
- **CLAUDE.md** con memoria jerárquica (usuario / proyecto / carpeta) y memoria automática.
- **Plan mode**, lista de tareas y preguntas al usuario para aclarar lo que pide.
- **Subagentes** (cada uno con su contexto, herramientas y modelo), **Skills** (carpetas con instrucciones y scripts), **comandos slash** propios y **plugins**.
- **Hooks:** antes y después de cada herramienta, al enviar un prompt, al detenerse; pueden bloquear o modificar lo que pasa.
- **Checkpoints / rewind**, permisos por herramienta y patrón, **worktrees** para trabajar en paralelo.
- `claude -p` sin interfaz, Agent SDK, GitHub Actions, *status line* y modo de salida personalizable.

### 1.6 iMovie
- **Temas y tráilers:** plantillas con títulos, transiciones y música ya combinados; *Magic Movie* arma un video automático con los clips que elijas.
- **Títulos animados**, transiciones de un clic y efecto **Ken Burns** en fotos.
- Corrección de color automática, estabilización, pantalla verde y *picture-in-picture*.
- **Ducking:** baja la música sola cuando hay voz. Biblioteca de música y efectos.
- Exportación a redes sociales con un clic.

### 1.7 DaVinci Resolve
- Páginas por etapa: **Media, Cut, Edit, Fusion, Color, Fairlight, Deliver**.
- **Edit:** herramientas *ripple, roll, slip y slide*, clips compuestos, multicámara y **keyframes** en cualquier parámetro.
- **Color:** ruedas (lift, gamma, gain), curvas, nodos, **LUTs** `.cube`, *scopes* (forma de onda, vectorscopio, histograma) y *color match*.
- **Fairlight:** mezclador por pista, EQ, compresor, normalización de volumen (LUFS) y **Voice Isolation**.
- **Neural Engine:** detección de escenas, *Smart Reframe*, *Magic Mask*, transcripción, edición por texto y subtítulos automáticos.
- **Deliver:** cola de render, presets y proxies o *optimized media*.

### 1.8 Blender
- Modelado, materiales **PBR** por nodos, iluminación, cámara y animación con **keyframes** y curvas.
- Motores de render **Eevee** (en tiempo real) y **Cycles** (trazado de rayos).
- Editor de video (VSE), *compositor* y *Geometry Nodes*.
- **API de Python (`bpy`)** y render sin interfaz: `blender -b archivo.blend -P script.py -o out_#### -a`.
- Importa y exporta glTF, FBX, OBJ y USD.

## Parte 3 — Las 15 fases

Cada fase se puede entregar por separado. El orden refuerza primero el núcleo (IDE + agente), después lo multimedia y al final el 3D, que es lo más costoso.

**Reglas para todas las fases:**
- Todo lo que el agente pueda hacer pasa por el sistema de aprobación que ya existe.
- Los modelos de datos puros van en `shared/` y se prueban con Vitest.
- Los textos de interfaz van en `i18n.ts` (es / en).
- Cada fase termina con `pnpm test`, `pnpm typecheck` y `pnpm lint` en verde.

---

### Fase 1 — Reglas y memoria de proyecto
**Inspiración:** Cursor Rules, CLAUDE.md, AGENTS.md de Codex.

**Entregables**
- Leer `AGENTS.md`, `CLAUDE.md`, `.cursor/rules/*.mdc` y `.github/copilot-instructions.md` de forma **jerárquica** (raíz → carpeta del archivo activo).
- Reglas propias en `.zinarix/rules/*.md`, con frontmatter `applies: always | glob | manual` y `globs: [...]`.
- Panel "Reglas activas" en el chat que muestre qué reglas entraron al contexto y cuántos tokens usan.
- `/init`: el agente genera un `AGENTS.md` a partir de lo que encuentra en el proyecto.

**Archivos:** `main/agent.ts`, `main/workspace.ts`, nuevo `shared/rules.ts`.

**Aceptación:** una regla con `globs: ["**/*.tsx"]` solo se inyecta cuando el contexto incluye un `.tsx`. Hay pruebas del parser y de la jerarquía.

---

### Fase 2 — Checkpoints, rewind y revisión de diffs
**Inspiración:** checkpoints de Cursor, `/rewind` de Claude Code, diffs de Codex.

**Entregables**
- Un checkpoint por turno del agente: guarda el contenido de cada archivo tocado en `runJournal`.
- Botón "Volver aquí" en cada mensaje, con tres opciones: restaurar código, restaurar conversación o ambas.
- Vista de **diff de todo el turno** (varios archivos) con aceptar o rechazar por bloque.
- Aviso claro de que lo que hizo `run_command` no se revierte (se mantiene la política actual).

**Archivos:** `main/runJournal.ts`, `main/agent.ts`, `renderer/components/Chat.tsx`, nuevo `DiffReview.tsx`.

**Aceptación:** al restaurar un checkpoint de 5 archivos, el disco queda byte a byte igual que antes del turno.

---

### Fase 3 — Modo plan, tareas y preguntas
**Inspiración:** plan mode de Claude Code y de Cursor.

La fase se entrega en dos partes. **3A (la base)** ya está en el código. **3B** convierte el plan de "un mensaje de texto" en algo que guía y controla la ejecución.

> Nota: `renderer/components/Plan.tsx` es el panel de **licencias** (planes Free/Pro), no el del agente. Lo de esta fase vive en `shared/agentModes.ts` y `renderer/components/AgentPlan.tsx`.

---

#### 3A — Base (hecha)

| Pieza | Dónde está | Qué hace |
|---|---|---|
| 4 modos y Shift+Tab | `shared/agentModes.ts` (`ChatMode`, `nextMode`), `ModeMenu` en `AgentPlan.tsx` | Preguntar / Plan / Agente / Auto. Los chats viejos (con el interruptor de agente) se migran con `modeFrom` |
| Modo Plan de solo lectura | `planAllows` + `PLAN_REFUSAL` en `main/agent.ts` | Las herramientas de escritura **ni se ofrecen** al modelo y, si las pide igual, se rechazan. Las de MCP solo pasan si su servidor las marca `readOnlyHint`. Los ayudantes (`delegate_to_ai`, `task`) heredan el modo Plan. Las CLI de agentes externos corren con `readOnly: true` |
| Formato del plan | `PLAN_PROMPT` | Objetivo / Pasos / Archivos / Riesgos, en el idioma del usuario |
| Aprobar, editar, rechazar | `PlanBar`, `PlanEditor`, `planStates` | "Aprobar" o "Aprobar y auto-aprobar". El estado sobrevive al reabrir el chat porque se deduce del siguiente mensaje (`isPlanApproval`) |
| Lista de tareas | `todo_write`, `parseTodos`, `TaskList` | Máximo 50 tareas, sin duplicados; avisa al modelo si deja más de una `in_progress` |
| Preguntas | `ask_user`, `parseQuestion`, `QuestionCard` | De 2 a 6 opciones, selección múltiple o respuesta libre; sin respuesta, el agente sigue y dice qué supuso |
| Pruebas | `test/agentModes.test.ts`, `test/planMode.test.ts` | Modos, parser de tareas y preguntas, estados del plan, rechazo en modo Plan |

**Huecos que deja 3A**
- El plan es solo texto. Al aprobarlo, el agente recibe el Markdown, pero nadie comprueba que lo siga: puede saltarse pasos o tocar archivos que el plan no menciona.
- Editar el plan es reescribir todo el texto a mano. No hay forma de decir "cambia el paso 3" y que el agente rehaga el plan.
- En modo Plan, `run_command` se rechaza siempre, incluso `git log` o `git diff`. El agente investiga peor que una persona con la misma consigna.
- El plan se pierde si se borra el chat, y no se puede reutilizar en otra conversación ni en una tarea en segundo plano (F5).
- El mismo modelo planifica y ejecuta. Lo normal es lo contrario: planificar con un modelo fuerte y ejecutar con uno más barato.
- El modo Auto aprueba ediciones, pero `run_command` sigue pidiendo aprobación siempre. Es correcto, pero el selector no lo dice, y el usuario cree que "auto" es auto para todo.
- `ask_user` espera la respuesta sin límite de tiempo. Si el usuario se fue, el turno se queda colgado.

---

#### 3B — El plan como contrato

**1. Plan estructurado**
- `parsePlan(markdown)` → `{ objetivo, pasos: [{n, texto, archivos[]}], archivos[], riesgos[] }`, función pura en `shared/agentModes.ts`. Acepta los encabezados en español y en inglés.
- Si al plan le falta una sección (por ejemplo, Archivos), la barra lo marca ("plan incompleto") y ofrece "Pedir que lo complete", sin bloquear la aprobación.
- Las rutas del plan se vuelven enlaces que abren el archivo. Las que no existen se marcan como "nuevo".

**2. Del plan a las tareas**
- Al aprobar, `planToTodos(plan)` crea la lista inicial de tareas con los pasos numerados. El agente arranca con la lista ya puesta y solo la actualiza.
- **Desvíos visibles:** al terminar, `planDrift(plan, archivosTocados)` compara lo que se tocó (lo da `turnFiles` de los checkpoints de la F2) con la sección Archivos. Muestra "Se cambiaron 2 archivos fuera del plan" con enlaces al diff. Solo informa, no revierte.
- Si el agente agrega una tarea que no venía en el plan, se marca como "nueva", para que el usuario vea que el alcance creció.

**3. Refinar en vez de reescribir**
- Botón **"Pedir cambios"** junto a Aprobar, Editar y Rechazar: un comentario libre o por paso ("el paso 3 sin dependencias nuevas"). El agente rehace el plan **en modo Plan**.
- Versiones del plan (v1, v2…) con un diff entre ellas. "Aprobar" siempre se aplica a la versión que está a la vista.

**4. Plan guardado**
- Al aprobarlo, el plan se guarda en `.zinarix/plans/<AAAA-MM-DD>-<slug>.md` con frontmatter (`status: approved | done | abandoned`, `model`, `conversation`). Ajuste para desactivarlo o para guardarlo fuera del repo (en `userData`).
- `/plan <archivo>` (o arrastrar el `.md`) lo retoma en otra conversación. En la F5, "Nueva tarea en segundo plano" acepta un plan aprobado como prompt.
- Al terminar todas las tareas, el frontmatter pasa a `done`.

**5. Modelo para planificar y modelo para ejecutar**
- Nuevo rol `planner` en `settings.roles` (junto a `agent`). En modo Plan se usa el `planner`; al aprobar, se ejecuta con el `agent`, salvo que el chat tenga un modelo propio.
- La barra del plan muestra con qué modelo se va a ejecutar y el costo estimado (pasos × costo medio por turno del modelo, según el historial de costos). El modelo se puede cambiar ahí mismo antes de aprobar.

**6. Comandos de solo lectura en modo Plan**
- `isReadOnlyCommand(cmd)`, función pura con una **lista permitida** cerrada: `git status | log | diff | show | branch | blame | ls-files`, `ls`/`dir`, `rg`/`grep`, `cat`/`type`, `node -v`, `pnpm -v`, `pnpm list`…
- Se rechaza cualquier cosa con `>`, `>>`, `|` hacia algo que no esté en la lista, `;`, `&&`, `||`, `` ` ``, `$(…)`, o argumentos que escriben (`git branch -D`, `git diff --output`). Ante la duda, se rechaza.
- Esos comandos corren sin pedir aprobación en modo Plan, con `cwd` fijo en el proyecto y un tiempo máximo de 30 s. Los demás siguen rechazados. **No** se permite correr las pruebas: ejecutan código del proyecto, que puede escribir.

**7. Modos más claros**
- Cada modo tiene su color y su icono en el borde del cuadro de texto, además del selector. En modo Plan se ve "Solo lectura" a la vista.
- Al pasar a Auto, un aviso de una línea (que se muestra una sola vez): "Las ediciones de archivos del proyecto se aprueban solas; los comandos y todo lo que sale de la máquina siguen pidiendo permiso". Es la misma regla que la tabla de la F5B, y la F5B la extiende con el sandbox.
- Auto nunca aprueba solo los archivos protegidos (`protectedWrite`: `.env`, `.git/`, ajustes de Zinarix). Esto ya ocurre porque `approvalKey` devuelve `null`; hay que dejarlo cubierto con una prueba.

**8. Preguntas que no cuelgan el turno**
- Varias preguntas en una sola tarjeta (hasta 4), para que el agente no haga cinco viajes.
- El modelo puede marcar una opción como **recomendada**, y la tarjeta la muestra primero.
- Tiempo de espera configurable (5 min por omisión). Al vencer, el agente sigue con la opción recomendada y lo dice. Botón "Decide tú", que hace lo mismo sin esperar.
- Si la app manda notificaciones (F5), una pregunta pendiente en una conversación que no está a la vista avisa con una notificación del sistema.

**9. Conexiones con otras fases**
- **F2:** aprobar un plan crea un checkpoint con nombre ("Antes del plan: <objetivo>"). "Volver al plan" restaura el código a ese punto y deja el plan abierto otra vez.
- **F4:** hook `PlanApproved` (recibe el plan en JSON), por ejemplo para crear un issue o avisar al equipo.
- **F15:** `omni agent -p "..." --mode plan --json` devuelve el plan estructurado de `parsePlan`, para usarlo en CI o revisarlo en un PR antes de ejecutar.

**Archivos**
- Cambios: `shared/agentModes.ts` (`parsePlan`, `planToTodos`, `planDrift`, `isReadOnlyCommand`, preguntas múltiples y opción recomendada), `main/agent.ts` (rol `planner`, comandos de solo lectura en Plan, tiempo de espera de `ask_user`, guardar el plan), `renderer/components/AgentPlan.tsx` (Pedir cambios, versiones, desvíos, modelo y costo de ejecución), `renderer/components/Chat.tsx` (color del modo, aviso de Auto), `renderer/store.ts` (ajustes nuevos), `renderer/i18n.ts`.
- Nuevo: `shared/planFile.ts` (leer y escribir `.zinarix/plans/*.md` con su frontmatter, función pura más pruebas).

**Pruebas (Vitest)**
- `parsePlan`: encabezados en es y en en, secciones que faltan, pasos con y sin rutas, Markdown raro (listas anidadas, bloques de código).
- `planToTodos` y `planDrift`: los pasos pasan a tareas en orden; archivos de más o de menos; rutas con `./` y `\` en Windows.
- `isReadOnlyCommand`: la lista permitida pasa; `git diff > x`, `ls; rm -rf .`, `git branch -D main`, `$(curl …)` y `cat a | sh` se rechazan.
- Auto: una edición de `.env` o de `.git/config` sigue pidiendo aprobación.
- `ask_user`: tiempo vencido → se usa la opción recomendada y el resultado lo dice.

**Aceptación**
- 3A (ya cumple): en modo Plan, cualquier herramienta de escritura se rechaza aunque el modelo intente usarla.
- 3B: un plan de 4 pasos aprobado arranca con 4 tareas en la lista; si el agente toca un archivo que no está en el plan, la conversación lo muestra al terminar.
- 3B: en modo Plan, el agente puede correr `git log -5` sin preguntar, pero `git log > out.txt` se rechaza.
- 3B: "Pedir cambios" en el paso 2 produce un plan v2 con el diff contra v1, sin tocar ningún archivo.
- 3B: planificar con un modelo y ejecutar con otro se refleja en el costo de cada turno.
- 3B: una pregunta sin respuesta durante 5 min no deja el turno colgado.

### Fase 4 — Subagentes, skills, comandos slash y hooks
**Inspiración:** Claude Code (subagentes, skills, hooks y plugins).

**Entregables**
- **Subagentes** definidos en `.zinarix/agents/*.md` (frontmatter: `model`, `tools`, `description`). El agente principal los lanza con `task(...)` y cada uno trabaja con su propio contexto. Se reutiliza `delegate_to_ai`.
- **Skills** en `.zinarix/skills/<nombre>/SKILL.md` (más scripts). Solo se carga la descripción hasta que se usan.
- **Comandos slash** propios en `.zinarix/commands/*.md`, con argumentos `$ARGUMENTS`.
- **Hooks** en `.zinarix/settings.json`: `PreToolUse`, `PostToolUse`, `UserPromptSubmit` y `Stop`. Un hook que termina con código 2 bloquea la acción y su salida le llega al modelo.

**Archivos:** `main/agent.ts`, `main/helper.ts`, nuevo `main/hooks.ts`, `renderer/commands.ts`.

**Aceptación:** un hook `PostToolUse` que corre `prettier` después de cada edición funciona. Un subagente con `tools: [read]` no puede escribir.

### Fase 5 — Agentes en paralelo con worktrees y sandbox
**Inspiración:** background agents de Cursor, Codex Cloud, worktrees de Claude Code, sandbox de Codex CLI.

La fase se entrega en dos partes. **5A (worktrees y tareas)** da casi todo el valor y no depende del sistema operativo. **5B (sandbox)** es la parte difícil, sobre todo en Windows, y no debe frenar a la 5A.

**Lo que ya existe y se reutiliza**
- `AgentScope.workspace` en `main/agent.ts`: cada ejecución del agente ya recibe su propia carpeta. Una tarea en segundo plano es una ejecución normal cuyo `workspace` apunta al worktree. No hace falta un segundo agente.
- `runJournal.ts`: ya guarda en disco las ejecuciones a medias. Se extiende para que las tareas sobrevivan a un cierre de la app.
- El sistema de aprobación (`tool_approval` / `ask`) y `blockedReason`.

**Huecos que hay que cerrar primero** (hoy permitirían que una tarea se salga de su worktree)
- `run_command` acepta cualquier `cwd` (`expandPath`). Dentro de una tarea, el `cwd` se limita al worktree y se rechaza lo demás.
- `run_command` acepta `admin: true`. En las tareas se desactiva siempre.
- La lista "Permitir siempre" (`alwaysAllow`) es por sesión. En las tareas es **por tarea**: lo que apruebas en una no se aplica a las demás.

---

#### 5A — Tareas en segundo plano con worktrees

**Crear la tarea**
- "Nueva tarea en segundo plano" (en el chat, la paleta y el panel Tareas): prompt, modelo, rama base (por omisión `HEAD`), nivel de aprobación y tope de costo.
- `git worktree add -b zinarix/<slug>-<id4> <ruta> <commit-base>`. Se guarda el **commit base** para poder calcular el diff aunque `main` avance.
- La ruta va **fuera del repositorio**, en `<userData>/worktrees/<hash-del-repo>/<id>`. Así el observador de archivos (`watch.ts`), el índice semántico, el LSP y la búsqueda del proyecto no ven los worktrees como archivos tuyos.
- **Cambios sin commit tuyos:** al crear la tarea se pregunta si se copian al worktree o si se parte del último commit. Nunca se tocan en tu árbol de trabajo.
- **Preparación del entorno:** un script opcional `.zinarix/worktree-setup` (por ejemplo `pnpm install --frozen-lockfile`) que corre al crear el worktree. Con pnpm es rápido porque comparte la *store*. Si no hay script, se avisa de que puede faltar `node_modules`.
- **Puertos:** cada tarea recibe un `PORT` propio en sus variables de entorno, para que tres servidores de desarrollo no choquen.
- Windows: se activa `core.longpaths` en el worktree para evitar errores de rutas largas.

**Mientras trabaja**
- Corren como máximo **3 tareas a la vez** (ajustable). Las demás esperan en cola.
- Estados: `en cola → preparando → trabajando → esperando aprobación → terminada | falló | cancelada | interrumpida`.
- **Las aprobaciones no bloquean la app:** una tarea que necesita aprobación pasa a "esperando aprobación", manda una notificación del sistema y espera; las demás siguen. Las aprobaciones pendientes de todas las tareas se ven juntas en el panel (atajos Y / N).
- **Tope de costo y de tiempo** por tarea: al llegar al tope la tarea se pausa y pregunta si sigue.
- Las reglas (F1), los checkpoints (F2) y los hooks (F4) se leen **del worktree**, no de tu carpeta, para que la tarea use la versión de su rama.
- Si la app se cierra, al volver a abrirla las tareas aparecen como "interrumpida", con su worktree intacto y un botón **Reanudar**.

**Panel Tareas** (`TasksPanel.tsx`)
- Por tarea: estado, modelo, rama, costo acumulado, tiempo, archivos cambiados (+/−) y la última acción.
- Abrir la tarea muestra su chat, su terminal y su diff, con el mismo componente de chat de siempre.
- Botones Pausar, Cancelar y "Abrir carpeta del worktree" (para mirarla o probarla a mano).

**Al terminar**
- El agente hace commit en su rama (con un trailer `Zinarix-Task: <id>`). El diff se calcula contra el commit base.
- **Fusionar:** si la rama base avanzó, primero se hace rebase dentro del worktree. Si hay conflictos, se ofrece "Resolver con el agente" (una tarea más) o resolverlo a mano. Nunca se fusiona encima de cambios tuyos sin commit que toquen los mismos archivos: se bloquea y se explica por qué.
- **Abrir PR:** `git push` + `gh pr create`, siempre con aprobación, porque publica fuera de la máquina. Se conecta con la revisión de la F6.
- **Mantener rama:** borra el worktree y conserva la rama.
- **Descartar:** `git worktree remove --force` y borrar la rama, con confirmación.
- **Limpieza:** `git worktree prune` al iniciar; aviso de cuánto disco ocupan los worktrees y opción de borrar automáticamente los que llevan más de N días sin abrirse.

#### 5B — Sandbox y niveles de aprobación

**Un solo control de modo.** Los niveles de esta fase no deben ser un segundo selector aparte de los modos de la F3. Se unifican en un solo control (Shift+Tab):

| Modo | Leer | Editar archivos | `run_command` | Red, nube, correo, navegador |
|---|---|---|---|---|
| Preguntar / Plan | Sí | No | No | No |
| Agente (por omisión) | Sí | Con aprobación | Con aprobación | Con aprobación |
| Auto en el worktree | Sí | Automático, solo dentro del worktree | Automático **solo si corre en el sandbox**; si no, con aprobación | Con aprobación |
| Acceso total | Sí | Automático | Automático | Con aprobación |

Las herramientas que actúan fuera de la máquina (`mail_send`, `vercel_*`, `supabase_query` de escritura, `git push`, publicar en un PR) **siempre** piden aprobación, incluso con acceso total.

**Sandbox para `run_command`**
- Reglas: escritura solo en el worktree y en la carpeta temporal; sin red, o red solo hacia una lista permitida (registro de npm, PyPI); sin acceso a `~/.ssh`, a la carpeta de datos de Zinarix ni a otros worktrees.
- **Variables de entorno limpias:** el comando no recibe tokens ni claves (`GITHUB_TOKEN`, `*_API_KEY`, lo que guarda `token-store.ts`). Esto se aplica en todas las tareas, aunque no haya sandbox.
- Por sistema operativo, en este orden de dificultad:
  - **Linux:** `bwrap` (bubblewrap). Si no está instalado, no hay sandbox.
  - **macOS:** `sandbox-exec` con un perfil generado. Está marcado como obsoleto por Apple, pero funciona y es lo que usa Codex CLI.
  - **Windows:** lo más difícil. Primera versión: **Job Object** (límite de procesos, memoria y que todo muera al cancelar) + token restringido y ACLs solo en el worktree. La red se bloquea con una regla del firewall por programa, o queda como "red no restringida" y se avisa. AppContainer completo queda para después. Se puede tomar como referencia el sandbox de Windows de Codex CLI (Apache-2.0), conservando su `NOTICE` si se reutiliza código.
- Detección al iniciar: el modo "Auto en el worktree" muestra qué protecciones están activas en esta máquina (escritura ✓, red ✗…). Si falta alguna, ese comando vuelve a pedir aprobación. Nunca se finge un sandbox que no existe.

- ✅ La Action abre el PR en un paso aparte, que es el único que recibe el token de GitHub.

**Mejoras**
- **Topes:** `--max-cost <usd>` (al pasarlo, el agente se detiene con salida 5, el código que ya está reservado) y `--timeout <min>`. En la Action, el tope de costo por omisión es de 2 USD.
- **Si el costo es desconocido** (`usd: null`, por ejemplo con un modelo que no está en el catálogo) y hay `--max-cost`, el agente se niega a arrancar, salvo que se pase `--allow-unknown-cost`. No debe gastar sin poder medir.
- **Sesiones:** cada ejecución guarda su transcripción en `.zinarix/runs/<id>.jsonl`. `--resume <id>` continúa una sesión y `--continue` retoma la última. El archivo `.zinarix/runs/` va al `.gitignore`.
- **Salida estructurada:** `--output-schema schema.json` obliga a que la respuesta final sea JSON válido según el esquema. Usa la misma lógica que el Playground de la F9, y si la respuesta no cumple, la salida es 6.
- **Permisos finos:** `--allow "run_command:pnpm *"` y `--deny "write_file:**/*.lock"`, con la misma sintaxis de patrones que la F4. `deny` siempre gana.
- **MCP** sin interfaz: lee `.zinarix/mcp.json`. Las herramientas de MCP cuentan como herramientas que salen de la máquina, así que en CI solo funcionan si se permiten de forma explícita con `--allow mcp:<servidor>`.
- **Subagentes** (`task(...)` de la F4) también en el modo sin interfaz, con el mismo tope de costo compartido.
- **Códigos de salida documentados:** 0 éxito, 1 error, 2 bloqueado por política o hook, 3 autenticación, 4 límite de uso, 5 tope de costo o tiempo, 6 salida que no cumple el esquema.

**Disparadores en GitHub** (todos fuera de PRs de forks: ahí GitHub no entrega secretos, y no se debe intentar rodearlo)
- `workflow_run`: cuando `ci.yml` falla en `main`, se lanza `agent-fix` con el log del fallo como contexto. Como máximo corre una vez por commit, para que no se repita en bucle.
- Etiqueta `zinarix-fix` en un issue: el agente intenta resolverlo y abre un PR. Solo funciona si la etiqueta la pone alguien con permiso de escritura.
- El PR que abre el agente nunca se fusiona solo y lleva el trailer `Zinarix-Agent: <id de la sesión>`.

#### 15C — Compartir con enlace de solo lectura

**Qué se comparte:** una conversación, el diff de un turno o de una tarea (F2 y F5), o una vista previa de video en baja resolución.

**Cómo funciona (cifrado de punta a punta, igual que `cloudSync`)**
1. Se arma un paquete con lo que se va a compartir.
2. Antes de subirlo, se le quitan los secretos con el detector de `packages/security`. Se muestra al usuario qué se quitó y tiene que confirmar.
3. El paquete se cifra con una **clave aleatoria nueva** y se sube a una tabla `zinarix_share` en el Supabase del usuario.
4. El enlace queda así: `https://<sitio>/s/<id>#<clave>`. La clave va después del `#`, así que **nunca llega a ningún servidor**: ni al de Supabase ni al del sitio.
5. Una página del sitio (`website/s/`) descarga el paquete y lo descifra en el navegador de quien abre el enlace.

- **Caducidad** de 1, 7 o 30 días, y botón **Revocar** (borra la fila en Supabase).
- Lista de "Mis enlaces" en el panel de la nube.
- **Fuera de alcance:** edición en tiempo real entre dos personas (al estilo Live Share). Es mucho trabajo y queda para después.

### 5.4 Hallazgo importante: el FFmpeg que va en el instalador es GPL

`apps/desktop/package.json` copia `node_modules/ffmpeg-static/ffmpeg` y `ffprobe` dentro del instalador (`extraResources` → `resources/ffmpeg`). El paquete `ffmpeg-static` tiene licencia **GPL-3.0-or-later**, y los binarios los compilan terceros (ShareX para Windows, johnvansickle para Linux, evermeet para macOS).

Distribuir FFmpeg como **programa aparte** está permitido y no vuelve GPL a Zinarix. Pero la GPL exige:
1. Incluir el texto de la licencia de FFmpeg junto al binario.
2. Avisar que se incluye y ofrecer el **código fuente exacto** de esa compilación (o un enlace a él).

Hoy no encontré ninguno de los dos. **Solución:** agregarlos en la fase 20, o cambiar a una compilación **LGPL** de FFmpeg (sin libx264). Conviene hacerlo antes del próximo lanzamiento público.

#### 16B — Partir `styles.css` en capas
**Cómo queda**
- Carpeta `renderer/styles/` con un archivo por área: `reset`, `base`, `chrome` (barra de título, actividad y estado), `editor`, `chat`, `terminal`, `explorer`, `git`, `settings`, `cloud` (Supabase, Vercel, Google Cloud), `mail`, `design`, `video` y `utilities`. Ninguno pasa de unas 1,000 líneas.
- El orden se declara **una sola vez**, al inicio de `tokens.css`: `@layer reset, tokens, base, components, features, utilities;`. Así deja de importar el orden de los `import` y la especificidad: una utilidad siempre le gana a un componente.
- Los 19 CSS de componentes también entran a su capa (`features`), no solo `styles.css`.

**La trampa que hay que evitar**
- En CSS, **lo que no está en ninguna capa le gana a todo lo que sí está**, sin importar la especificidad. Monaco y xterm inyectan su CSS sin capa. Si nuestros ajustes sobre `.monaco-editor` o `.xterm` entran a una capa, **dejan de aplicarse**, y el editor o la terminal cambian de aspecto sin aviso.
- Por eso esos ajustes van en `styles/overrides.css`, **fuera de las capas**. Es el único archivo que puede estar así, y la prueba lo verifica.

**Cómo se hace sin romper nada**
1. Primer paso, mecánico: envolver todo `styles.css` en `@layer features { … }` y comparar capturas. Dentro de una sola capa la cascada no cambia, así que no debería moverse nada. Si algo se mueve, es un choque con el CSS de Monaco o de xterm, y esa regla pasa a `overrides.css`.
2. Después, mover bloques a sus archivos **sin cambiar ni una regla**, en commits pequeños, cada uno con su comparación de capturas.
3. Al final, bajar a `base` y `reset` lo que corresponda.

**Pruebas** (se agregan a `test/uiTokens.test.ts`)
- Todo CSS del renderer está dentro de un `@layer`, salvo `overrides.css`.
- `overrides.css` solo tiene selectores de Monaco, xterm o del sistema (`::-webkit-scrollbar`).
- Ningún archivo de `styles/` pasa de 1,200 líneas.

#### 16C — Primitivas React
