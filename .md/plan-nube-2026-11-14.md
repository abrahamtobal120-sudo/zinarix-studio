# Plan: Zinarix en la nube ("cada quien conecta la suya")

Fecha: 2026-11-14

Idea central: Zinarix **no pone servidores**. Cada usuario conecta *su* Supabase, *su* túnel
y *su* nube (Google Cloud, Fly, Railway o un VPS). Costo para Zinarix ≈ $0 por usuario;
costo para el usuario ≈ $0 en los planes gratis (Supabase free, Cloud Run que escala a cero).

Orden: 1 → 2 → 3. Cada fase reutiliza la anterior.

---

## Fase 1 — Sincronización con el Supabase del usuario

**Qué ya existe**
- `apps/desktop/src/main/supabase.ts`: cuentas de Supabase conectadas, proyectos, SQL por la Management API.
- `packages/core/src/db.ts`: SQLite local (`omni.db`) con `conversations`, `messages`, `usage`.
- `packages/core/src/vault.ts`: llaves de API (keychain / archivo cifrado).
- `desktop.json` y `config.json` (ajustes), memorias (`list_memories`).

**Qué hay que hacer**
1. **Elegir proyecto**: en Ajustes → "Nube", el usuario elige uno de sus proyectos de Supabase
   (o crea uno nuevo "zinarix-sync" con un clic).
2. **Instalar el esquema** en ese proyecto (una migración por la Management API):
   `zinarix_sync(kind text, id text, updated_at bigint, deleted bool, device text, blob bytea, primary key(kind,id))`, con RLS activado.
3. **Cifrado de punta a punta**: frase de sincronización → `scrypt` → llave AES-256-GCM.
   Supabase solo guarda blobs cifrados; ni Supabase ni Zinarix pueden leerlos.
4. **Qué se sincroniza**: chats + mensajes, ajustes no secretos, memorias, uso/créditos.
   Las llaves de API **no** por defecto; opción explícita "sincronizar llaves" (van cifradas igual).
5. **Motor**: nuevo `apps/desktop/src/main/cloudSync.ts`. Cada fila con `updated_at`;
   subir lo cambiado, bajar lo más nuevo, "gana la última escritura", borrados como marca `deleted`.
   Se dispara al guardar un chat y cada X minutos. Para el acceso a datos: pedir las llaves del
   proyecto por la Management API y hablar con PostgREST (la API de SQL tiene límite de uso).
6. **Core**: migración 3 en `db.ts` → columna `sync_rev`/`deleted_at` en `conversations` y `messages`.
7. **UI**: panel "Nube" (estado, última sync, botón "Sincronizar ahora", "Desconectar").

Esfuerzo: unos días. Riesgo: bajo.

## Fase 2 — Zinarix en el navegador

**Qué ya existe**
- `phone.ts` + `phonePage.ts`: servidor HTTP en la PC (puerto 47390) con la página del celular.
- `tunnel.ts`: cloudflared verificado con SHA-256 → dirección https pública.
- `pairing.ts`: PIN + protección contra fuerza bruta.
- `packages/server`: reservado para "Fastify + WebSocket" (todavía vacío).

**Qué hay que hacer**
1. **`packages/server`**: servidor Fastify + WebSocket que expone las mismas llamadas que hoy
   pasan por IPC (`handle('ai:...')` en `main.ts`). Sacar esos handlers a un módulo común para
   que IPC y WebSocket usen el mismo código.
2. **Shim web del renderer**: el renderer React usa `window.api` (preload). Un `webApi.ts` que
   implemente la misma interfaz por WebSocket → el mismo `App.tsx` corre en el navegador.
3. **Servirlo** desde la PC del usuario por el túnel que ya existe (como el celular hoy,
   pero con la interfaz completa). Emparejamiento con PIN igual que ahora.
4. **Modo "PC apagada"**: si la PC no responde, la web lee los chats sincronizados de la Fase 1
   (solo lectura, descifra en el navegador con la frase).
5. Página de entrada en `website/` (`/app`) donde el usuario pega su dirección o escanea un QR.

Esfuerzo: medio. Riesgo: medio (seguridad del canal; ya hay base con PIN y túnel).

## Fase 3 — Espacio de trabajo en la nube del usuario

Mismo servidor de la Fase 2, pero corriendo **en la nube del usuario** en vez de en su PC.

1. **Imagen Docker** `zinarix-server` (core + server + terminal + git), publicada en GHCR
   firmada. Sin interfaz de escritorio; la interfaz es la web de la Fase 2.
2. **Desplegar con un clic** desde Zinarix, usando las cuentas que el usuario ya conecta:
   - Google Cloud Run (`gcloud.ts` ya existe) — escala a cero, prácticamente gratis si no se usa.
   - Fly.io / Railway / VPS propio por SSH como alternativas (token del usuario).
3. **Disco persistente** para el proyecto: volumen de Fly, o bucket de Cloud Storage montado
   en Cloud Run. Los chats se guardan en el Supabase de la Fase 1.
4. **Llaves de API**: viven como secretos en la nube del usuario (Secret Manager / secrets de Fly),
   nunca en servidores de Zinarix.
5. **Seguridad**: es el servidor del propio usuario y solo corre su código. Acceso con
   token de emparejamiento + PIN, HTTPS obligatorio, apagado automático por inactividad.

Esfuerzo: grande. Riesgo: medio. Costo para Zinarix: $0.
